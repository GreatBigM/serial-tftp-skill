# 技能失败处理原则

## 核心原则

**技能失败 → 排查原因 → 改进技能。不绕过。不造参数。**

## 标准流程

当技能（脚本/工具）执行失败时：

```
技能失败
  → 1. 读技能文档（README / Usage / --help）
  → 2. 看有没有未用过的参数能处理当前场景
  → 3. 读失败信息，理解失败原因
  → 4. 如果技能有 bug → patch 技能本身（skill_manage action=patch）
  → 5. 如果技能缺功能 → 扩展技能（加参数/加分支）
  → 6. 只有技能完全不适用 → 才创建新技能
```

## 成功使用的技能也要优化

技能执行成功 ≠ 没有优化空间。每次使用后思考：

- 速度能优化吗？（更快的执行路径、合并步骤）
- 逻辑更合理？（更好的错误提示、更清晰的流程）
- 参数更合理？（默认参数是否最优）
- 遗漏了什么？（文档中没覆盖的反模式、新发现的问题）

## 反面案例（2026-06-25 HM6801）

`auto-uboot-interrupt.py flash` 执行失败，输出 `Device mode: unknown`。

**错误做法：** 不读错误信息、不看 Usage/--help、直接手动 U-Boot 命令烧录 → `sf erase 0 0x100000` 只擦 1MB + `sf write 0 0x1000000` 写 16MB → NOR 未擦区域损坏 → U-Boot 启动区被破坏 → 设备变砖。

**正确做法应该：**
1. 读 script Usage → 发现已有 `--at-uboot` 参数用于设备已在 U-Boot 的场景
2. 确认设备状态：串口敲回车看返回 — `PRJ009#` 表示已在 U-Boot
3. 用正确参数重试：`python3 auto-uboot-interrupt.py flash --at-uboot`
4. 如果 `--at-uboot`也失败 → 查脚本源码分析失败根因
5. 修脚本（补充模式检测逻辑）→ commit → 再试

## 检查清单

- [ ] 读了技能的 Usage/--help？
- [ ] 理解了失败的具体原因？
- [ ] 技能有没有参数能覆盖当前场景？
- [ ] 如果修技能，改动是否最小？
- [ ] 修完技能后，是否把反模式写入了技能文档？
- [ ] 技能执行成功了，有没有可以优化的点？
